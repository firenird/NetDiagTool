                 NetDiag Tool-1.2.0 - Security Review  

                

              Summary  

              NetDiag Tool v1.2 was built with security controls in six areas, and each control listed here exists in the  
              source code and is covered by an automated test where one is named. This is a developer self-review of  
              the design and code, not an independent audit or penetration test.  

              Scope: the full v1.2 source —  NetDiagTool.Core (all network, monitoring, email, storage and CLI logic),  
              NetDiagTool.ViewModels, the WPF GUI and NetDiagCli. The test suite (110 tests) runs on loopback only.  
              All 110 pass on Linux; the latest Windows run you shared was an earlier build (102 of 103 passed, and  
              the one failure was a test timeout since fixed).  

              Overall posture: credentials are encrypted and never logged; the tool only reads system state and never  
              changes other processes; untrusted input (CSV, network replies, backups, DNS responses) is bounded  
              and validated; nothing leaves the machine except tests the user starts and email the user configures.  
              The main residual risks are listed in the last section.  

              Credential and secret protection  

              The only secret the tool stores is the SMTP password, and it is never written anywhere in plain text.  

                   •    Encrypted at rest with Windows DPAPI. The password is encrypted with CryptProtectData  
                        (current-user scope, plus an app-specific entropy value) and saved in config.json as  
                        dpapi:<base64>. Only the same Windows user on the same PC can decrypt it.  
                   •    Plaintext is refused.  If config.json contains a password value without the dpapi: prefix, it is  
                        cleared on load and the user is told to re-enter it.  
                   •    No DPAPI, no saving. On a system without DPAPI the GUI refuses to store the password rather  
                        than falling back to plain text.  
                   •    Kept out of every other file.  Monitoring profiles, jobs, exports, reports and backups have no  
                        password field. The diagnostics bundle removes both the encrypted password and the SMTP  
                        username.  
                   •    Never round-tripped in the UI. The password box pushes its value to the view model and is  
                        cleared after save; the stored password is never read back into the screen.  
                   •    Not accepted on the command line.  --password,  --pass,  --pwd,  --smtp-password,  --secret  
                        and --token are rejected with exit code 2, because arguments are visible in process lists and  
                        shell history.  
                   •    Redacted from SMTP transcripts. The "Test SMTP Connection" transcript shows AUTH PLAIN  
                        *** and *** (password) instead of the base64 credentials.  
                   •    Clear failure on another PC. A password copied in a backup to a different user or machine fails  
                        with a message to re-enter it, instead of a silent error.  

              Logging and data privacy  

              Everything the tool records stays on the local disk, and obvious secrets are masked before any line is  
              written.

               Network and listener safety  

               Every network operation has a timeout, a size limit and a cancel path, so a slow or hostile peer cannot  
              hang or exhaust the tool.  

              Port listeners (the only feature that accepts inbound connections)  

                   •    At most 100 concurrent connections per listener; extra clients are refused and logged.  
                   •    Received data is capped at 64 KB per read cycle, and a client that sends nothing is closed after  
                        the receive timeout (default 5 s).  
                   •    On Windows the port is bound with exclusive address use, so another program cannot share or  
                        take over the port, and "Port already in use" is reported clearly.  
                   •    Duplicate listeners inside NetDiag are blocked; ports below 1024 trigger a warning.  
                   •    The listen address is the user's choice: 127.0.0.1  keeps a listener local-only, 0.0.0.0 exposes it  
                        to the network.  
                   •    All listeners and their client connections are stopped and disposed of when the app closes.  

              Outbound tests and replies

                   •    Custom TCP message replies are capped at 64 KB; a reply is never invented when the server  
                        sends nothing; Telnet negotiation bytes are stripped, and control characters are shown escaped.  
                   •    tracert has a hard time limit and is killed on cancel or app exit.  
                   •    Bulk concurrency is limited to 1-200 (trace 1-20).  

              SMTP  

                   •    Server certificates are validated by default.  
                   •    In STARTTLS mode the connection fails if the server does not offer STARTTLS, so it never silently  
                        falls back to plain text.  
                   •    "Accept invalid certificates" exists for internal servers with self-signed certificates; it is off by  
                        default.  
                   •    SMTP failures are queued, retried twice and logged; they never stop monitoring or mark a  
                        network test as failed.  

               DNS client (raw queries to chosen servers)  

                   •    A response must carry the matching transaction ID and the response flag; every field is bounds- 
                        checked; name-compression loops stop after 20 jumps.  
                   •    Query times are measured; on timeout no time is reported.  

               Process and OS interaction  

              The tool runs with the user's normal rights and only reads system state; it never changes another  
               process, a connection or a Windows setting on its own.  

                   •    No administrator rights. The manifest requests asInvoker. Admin is needed only if Windows  
                        itself requires it for a specific reserved port.  
                   •    Least-privilege process queries.  Port Monitor and process details open other processes with  
                        PROCESS_QUERY_LIMITED_INFORMATION only (path, command line, parent, user). Access denied  
                        or a process exiting mid-query just leaves a field empty.  
                   •    Read-only Port Monitor.  It lists TCP/UDP endpoints through GetExtendedTcpTable /  
                        GetExtendedUdpTable. It does not close connections or end processes; it links to Task Manager  
                        and Resource Monitor, where the user acts with Windows' own controls.  
                   •    Signature check without network calls. The Authenticode check uses WinVerifyTrust with  
                        cache-only URL retrieval and no revocation lookup, so selecting a row never triggers outbound  
                        traffic.  
                   •    Child processes by full path, no shell. tracert.exe and schtasks.exe are started from  
                        %SystemRoot%\System32 with a hidden window, which avoids picking up a planted copy from  
                        the working folder or PATH.  
                   •    Scheduled tasks run as the current user. "Create Windows task" registers NetDiagCli.exe job  
                        run <name> for the signed-in user, without elevation, and only after the user confirms the exact  
                        command.  
                   •    Crash handling. Unhandled UI errors are logged and shown with secrets masked; the app keeps  
                        running.

              Backup, restore and file handling  

              A backup file is treated as untrusted input: restore only accepts NetDiag's own files and can never write  
              outside the data folder.  

                   •    Zip-slip protection.  Every entry's final path is resolved and must sit inside the NetDiag data  
                        folder; entries like Data/../../file are skipped.  
                   •    Allow-list. Only config.json, Profiles/, Jobs/ and Data/ are restored; anything else in the  
                        ZIP is ignored.  
                   •    Manifest required. A ZIP without a NetDiag manifest.json is rejected as "not a NetDiag  
                        backup".  
                   •    Config validated before writing. A restored config.json goes through the same validation and  
                        clamping as a normal load.  
                   •    Safety backup first. The current state is backed up automatically before any  restoration.  
                   •    Atomic writes. config.json, profiles, jobs and incidents are written to a temp file and then  
                        swapped in, so a crash never leaves a half-written file.  
                   •    Portable data location. All data stays next to the EXE; if that folder is read-only, the tool uses  
                        %LOCALAPPDATA%\NetDiagTool instead of failing. Nothing is written to the registry.  

              Capabilities deliberately excluded  

              The build spec's Security / Safety section ruled out the following, and none of them exist in the code:  

                   •    Credential harvesting — the listener shows what clients send for troubleshooting but have  no  
                        login prompts or credential capture.  
                   •    Exploitation or vulnerability scanning.  
                   •    Packet capture or traffic interception — the tool only sees its own sockets and the OS  
                        connection tables.  
                   •    Offensive scanning automation —  bulk tests run only against targets the user lists, with bounded  
                        concurrency.  
                   •    Process termination and closing other programs' connections —  Port Monitor stays read-only.  
                   •    Telemetry, cloud services, remote agents or auto-update.
